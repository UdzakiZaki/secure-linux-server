# SELinux и Nginx: каталог сайта и контроль доступа

## Исходная настройка

В [конфигурации Nginx](../configs/nginx/nginx.conf) задано `root /srv/site;`, а [diff](../configs/nginx/nginx.conf.diff) показывает замену стандартного `/usr/share/nginx/html`. Сохранены [локальное правило контекстов](../evidence/selinux/selinux-02-local-rules.txt), [фактические метки](../evidence/final/05-site-label.txt), [режим Enforcing](../evidence/final/02-selinux.txt) и успешные HTTP-запросы.

Сервер работает на [CentOS Stream 10](../evidence/environment.txt). Дополнительно передал исходный ответ 403, ошибку Nginx, AVC и результат перемаркировки; эти фрагменты собраны в [дополнении по диагностике](../evidence/selinux/selinux-04-diagnosis-supplement.txt). Они связывают ошибку доступа с типом файлов и показывают исправление без отключения SELinux.

## Unix-права и политика SELinux

SELinux дополняет права владельца, группы и остальных пользователей проверкой политики безопасности. При `Enforcing` запрещённая политикой операция блокируется, даже если Unix-права её разрешают. Следовательно, изменение `root` сообщает Nginx путь к сайту, но само по себе не предоставляет доступ к этому пути.

В данном проекте каталог принадлежит `deploy:nginx` и имеет режим 750, страница — 640: владелец может менять содержимое, группа — читать файл и проходить в каталог, остальные такого доступа не получают. Это видно в [выводе ls](../evidence/final/05-site-label.txt). В [nginx.conf](../configs/nginx/nginx.conf) задан пользователь `nginx`; чтение владельцем и отказ nobody подтверждены [проверкой deploy](../evidence/users/05-owner-can-read.txt) и [проверкой nobody](../evidence/users/06-other-user-denied.txt).

Отказ обычному admin при просмотре страницы — отдельный наблюдаемый случай: [ls сообщает Permission denied](../evidence/users/03b-admin-denied-on-site-dir.txt), тогда как [HTTP продолжает работать](../evidence/users/04-site-still-200.txt). Сохранённое членство admin в [группах](../evidence/users/13-admin-id.txt) не включает nginx; режим каталога объясняет отсутствие доступа без sudo. Этот отказ нельзя использовать как доказательство блокировки Nginx со стороны SELinux.

## Домен процесса и тип содержимого

В [AVC-событии](../evidence/selinux/selinux-04-diagnosis-supplement.txt) процесс Nginx имеет контекст `system_u:system_r:httpd_t:s0`. Домен `httpd_t` — тип безопасности процесса; тип файла указывает политике назначение объекта. Для статического веб-содержимого используется `httpd_sys_content_t`: политика разрешает соответствующему веб-домену читать такое содержимое, но не предоставляет ему произвольную запись.

У страницы в `/srv/site` до исправления был тип `var_t`, что подтверждают исходный `ls -Z` и поле `tcontext` в том же дополнении. Такой общий тип не обозначает веб-содержимое и не даёт домену `httpd_t` нужного доступа. Поэтому корректного пути в Nginx и достаточных Unix-прав было недостаточно: требовалось согласовать тип содержимого с политикой SELinux.

Подтверждённая метка страницы в [материалах проверки](../evidence/selinux/selinux-01-label-after.txt):

```text
unconfined_u:object_r:httpd_sys_content_t:s0 index.html
```

Для доступа по типам здесь существенен компонент `httpd_sys_content_t`. Начальное `unconfined_u` — поле пользователя SELinux в метке файла; оно не означает, что процесс Nginx работает без ограничений. [Итоговый вывод](../evidence/final/05-site-label.txt) подтверждает нужный тип и для каталога, и для `index.html`.

## HTTP 403 и роль журнала аудита

При обращении к `http://localhost` сервер вернул `HTTP/1.1 403 Forbidden`. В [журнале Nginx](../evidence/selinux/selinux-04-diagnosis-supplement.txt) в 19:15:08 зафиксировано:

```text
"/srv/site/index.html" is forbidden (13: Permission denied)
```

Один такой ответ не различает причины отказа. Я проверил события через `sudo ausearch -m avc -ts recent`; запись за ту же секунду относится к Nginx и тому же файлу. Существенные поля из [AVC](../evidence/selinux/selinux-04-diagnosis-supplement.txt):

```text
avc: denied { getattr }
comm="nginx"
path="/srv/site/index.html"
scontext=system_u:system_r:httpd_t:s0
tcontext=unconfined_u:object_r:var_t:s0
tclass=file
permissive=0
```

`getattr` означает получение атрибутов файла: именно эта операция запрещена в записи. Её нельзя пересказывать как зафиксированный отказ `{ read }`, хотя запрет на получение атрибутов уже мешает обслуживанию страницы. `scontext` показывает домен процесса, `tcontext` — тип объекта, а `permissive=0` указывает, что отказ применялся. Совпадение времени, процесса и пути связывает HTTP 403 с блокировкой SELinux.

Отдельный [вывод ausearch по ключу nginx_config](../evidence/audit/05-ausearch-key.txt) фиксирует успешное изменение `/etc/nginx/nginx.conf`, а не этот отказ. Наблюдение за конфигурацией и диагностика AVC решают разные задачи, хотя оба используют журнал аудита.

## Постоянная настройка: semanage fcontext и restorecon

В [локальных правилах](../evidence/selinux/selinux-02-local-rules.txt) сохранена запись:

```text
/srv/site(/.*)?                                    all files          system_u:object_r:httpd_sys_content_t:s0
```

Выражение охватывает сам каталог и его содержимое. Правило добавлено через `semanage fcontext`, после чего выполнен `sudo restorecon -Rv /srv/site`. Первая команда сохраняет соответствие пути и ожидаемого контекста; вторая применяет это соответствие к фактическим меткам файлов. В [выводе restorecon](../evidence/selinux/selinux-04-diagnosis-supplement.txt) для каталога и страницы зафиксирован переход `var_t` → `httpd_sys_content_t`.

Для воспроизведения сохранённой настройки на сервере, где такого локального правила ещё нет, используется следующая последовательность. Строка `semanage` записана по сохранённому правилу.

```bash
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/site(/.*)?'
sudo restorecon -Rv /srv/site
```

Если такое локальное правило уже существует и отличается, для его изменения применяется `-m` вместо `-a`. Повторное добавление не требуется, если сохранено нужное значение.

Постоянное соответствие позволяет восстановить правильные метки при повторном `restorecon` и полной перемаркировке. Оно не меняет владельца, Unix-права и `root` Nginx. Перемещённые файлы могут сохранить прежние метки: после размещения содержимого фактический тип нужно проверять и при необходимости восстанавливать.

`chcon` меняет текущую метку объекта без создания такого соответствия пути. Изменение может пережить обычную перезагрузку, но последующий `restorecon` или полная перемаркировка восстановят контекст по правилам. Поэтому для постоянной конфигурации важна связка «правило пути + применение меток»; `chcon` не заменяет её.

## Проверка результата

Сохранённые проверки подтверждают несколько независимых условий:

| Условие | Команда или проверка из материалов | Результат и источник |
|---|---|---|
| SELinux включён в режиме применения запретов | `getenforce` | [Enforcing](../evidence/final/02-selinux.txt) |
| Каталог и страница размечены | `sudo ls -lZd /srv/site /srv/site/index.html` | [httpd_sys_content_t](../evidence/final/05-site-label.txt) |
| Локальное соответствие пути сохранено | Снимок локальных правил fcontext | [Правило для /srv/site](../evidence/selinux/selinux-02-local-rules.txt) |
| Синтаксис Nginx корректен | `sudo nginx -t` | [test is successful](../evidence/audit/07-nginx-config-test-after-revert.txt) |
| Сайт доступен локально | `curl -sI http://localhost` и `curl -s http://localhost` | [HTTP 200](../evidence/final/03-site-headers.txt), [страница](../evidence/final/04-site-body.txt) |
| Сайт доступен с хоста | Сохранённые заголовки и тело ответа | [HTTP 200](../evidence/final/08-site-from-host.txt), [Test site](../evidence/final/09-site-body-from-host.txt) |

В [дополнении по диагностике](../evidence/selinux/selinux-04-diagnosis-supplement.txt) повторный локальный запрос после `restorecon` возвращает 200 вместо 403. Последующие итоговые проверки подтверждают правильные метки, режим `Enforcing` и выдачу ожидаемой страницы локально и с хоста.

## Почему SELinux оставлен включённым

Отключение SELinux снимает проверку политики, но не исправляет неверное соответствие пути и типа. Для веб-сервера это также убирает дополнительный барьер доступа к объектам за пределами разрешённого содержимого. Правильная метка сохраняет разграничение доступа и позволяет обслуживать сайт при действующей политике.

В этой работе подтверждены одновременно [Enforcing](../evidence/final/02-selinux.txt) и [HTTP 200](../evidence/final/03-site-headers.txt). Они показывают, что для сохранённой конфигурации отключение SELinux не требуется. Сводный ход работы — в [журнале](work-log.md).
